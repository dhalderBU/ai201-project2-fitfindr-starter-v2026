## What This Does

<!-- Three or four sentences: what a user asks for, and what they get back. -->
This application searches for clothing and garments(from listing) based on inputs 
like a) description b)size and c) price. 
The system generates search results from listing (if available) and then generates 
Outfit based on wardrobe and a fit card statement for social media postingwhich is 
caption on the find
It also compares the selected item's price with the average of other listings
in the same category and displays a warning when it is above that average.
This comparison uses the supplied dataset and makes no additional model call.

### `search_listings`

- **What it does:**  Search the listings data for items matching a description, 
and optionally a
    size and a price ceiling.
- **Inputs:** `description` (str), `size` (str | None), and `max_price` (float | None). 
where description is set of keywords describing what the user wants, Size is a 
string to filter like "W30 L30" or "L" . max_price is maximum price inclussive. 
Or one could enter None to skip priec fiktering.
- **Returns:** A list of matching listing dictionaries (sorted with best match 
first based on score) containing fields such as title, description,category,style
 tags, size, condition, price, colors, brand, and platform. If nothing is found 
 based on the descriptive keywords put as input then returns an empty 
 list (doesnt return none or exception)
- **When it has nothing:** Returns an empty list (`[]`).

### `suggest_outfit`

- **What it does:**  Given a thrifted item and the user's wardrobe, suggest one or 
two outfits. This function calls the model using generate function 
- **Inputs:** `new_item` (a dictionary containing the listing's title, description, 
category, style tags, size, condition, price, colors, brand, and platform) and 
`wardrobe` (a dictionary with an `items` key whose value is a list of 
wardrobe-item dictionaries).
- **Returns:** A non-empty string containing outfit suggestions based on the 
wardrobe(as generated by the LLM) or general styling advice when there the wardrobe 
passed is empty.
- **When it has nothing:** If the wardrobe is empty, returns general styling advice 
instead of raising an error.

### `create_fit_card`

- **What it does:** Creates a two-to-four-sentence social-media caption using the LLM 
to describe the new find, its title, outfit, price, platform, and overall vibe.
- **Inputs:** `outfit` (a string returned by `suggest_outfit`) and `new_item` (a 
listing dictionary returned by `search_listings`).
- **Returns:** A two-to-four-sentence fit-card caption as a string.
- **When it has nothing:** If `outfit` is empty or contains only whitespace, returns 
a message asking for an outfit suggestion.

### `compare_price` — fourth tool (Stretch feature -1)

- **What it does:** Compare the selected listing with every other listing in
  `data/listings.json` with the same category, excluding its own ID. Search
  keywords, size, and budget do not restrict the comparison group.
- **Input:** `new_item` (dict): a complete listing returned by `search_listings`,
  including `id` (str), `category` (str), and `price` (float).
- **Returns:** A dictionary containing `listing_id` (str), `category` (str),
  `item_price` (float), `comparison_count` (int), `average_price` (float or
  None), `difference` (float or None), and `status` (str). The average is
  `sum(prices) / len(prices)`, rounded to cents. The difference is the item
  price minus that rounded average, also rounded to cents. A positive, negative,
  or zero difference gives `above_average`, `below_average`, or `at_average`.
- **When it has nothing:** Return `comparison_count=0`, `average_price=None`,
  `difference=None`, and `status="insufficient_data"`.

This tool uses `load_listings()` and Python built-in functions; Category averages 
mix garment types, brands, and conditions, so they are a broad dataset reference, 
not evidence of any other statistical significance for this app.

## Planning Loop

<!-- Your branch rule, stated as a rule — the condition AND both paths — plus
     the file and function that holds it.

     Like this:
       "If search_listings returns an empty list, put a message in the session
        and stop. Otherwise take the first result and go to suggest_outfit."
        — agent.py::run_agent

     The grader checks your code against what you claim here, so the file and
     function have to be real. -->

**Below includes 2nd Branch too**

**Branch rules:** In `agent.py::run_agent`, if `search_listings` returns an empty
list, put a useful message in the session and stop. Otherwise, skip listings
that appear in the wardrobe by category, meaningful name, and shared color;
stop with a message if all results are owned. Store the first unowned result
as the selected item, then call `compare_price`.

The new stretch branch checks whether
`session["price_comparison"]["status"] == "above_average"`. If true, store
`session["price_warning"]`, record `above-average price branch (Second Branch)` in the trace,
and display the warning in the CLI. Otherwise leave the warning as `None` and
record `price comparison: no warning`. Both paths continue to `suggest_outfit`
and `create_fit_card` with the same selected item. No comparison or model tool
is called after an empty-search or all-owned stop. If there are no comparison
peers, show that the average is unavailable and continue without a warning.

**Where it lives:** The `branch rule` is implemented in the `run_agent` function in agent.py.

**How the query is parsed:** Regular expressions extract the description, optional 
size, and maximum price from the user’s query. The function removes the size and 
price phrases from the description, converts the price to a float, and returns 
all three values in a dictionary.

**What moves through the session:** The parsed query and search results are
stored in `session["parsed"]` and `session["search_results"]`. The first unowned
result becomes `session["selected_item"]`. `compare_price` reads that item and
its return value is stored in `session["price_comparison"]`; the branch reads
that stored result and may set `session["price_warning"]`. The selected item
and wardrobe then go to `suggest_outfit`, whose output is stored as
`session["outfit_suggestion"]`. The outfit and a copy of the item are saved in
`session["fit_card_inputs"]` and passed to `create_fit_card`; its output is
stored as `session["fit_card"]` and appended to `session["fit_card_outputs"]`.
The price warning is displayed separately from the caption.

**Gap in specs that needs addressing :** Clothing items use different sizing systems—for 
example, tops may use sizes such as `S`, `M`, or `L`, while pants may use measurements 
such as `W30 L30`. The specification should define how each type of size is matched and 
how universal-size items are handled.

### Style memory — one editable wardrobe (Stretch feature 3)

```bash
python app.py wardrobe list
python app.py wardrobe add --name 'Purple trousers' --category bottoms --colors purple --style-tags casual
python app.py wardrobe remove --id w_011
python app.py ask 'vintage graphic tee under $30' --trace
```

Use the ID printed by `add` or `list` when removing an item; `w_011` above is
an example. Categories are `tops`, `bottoms`, `outerwear`, `shoes`, and
`accessories`. Multiple colors and style tags are accepted, and `--notes`
can add optional text. Quote multiword values, for example `--colors 'dark blue'`.
Only add pieces you own; a search recommendation does not add an item.

**Where it is implemented:** All storage helpers are in
`utils/data_loader.py`: `load_wardrobe()` returns `(wardrobe, source)`,
`save_wardrobe(wardrobe)` validates and saves it, and `add_wardrobe_item(...)`
and `remove_wardrobe_item(id)` save the change and return `(item, total_count)`.
`app.py::cmd_wardrobe` exposes those operations. `app.py::cmd_ask` loads the
saved wardrobe and passes it into `run_agent`; the returned session records
`wardrobe_source`, and the trace names the loaded items. Interactive searches
reload memory between queries so changes from another CLI command are picked up.

**What changed:** Previously every CLI invocation reloaded the fixed example.
Now the first invocation initializes `.fitfindr/wardrobe.json` from that example,
and subsequent invocations use the saved contents. Removing all items leaves
an empty wardrobe; it does not repopulate the example. `--empty-wardrobe`
bypasses saved memory for a single run without changing it. Invalid memory,
blank item names, duplicate items, invalid categories, and unknown removal IDs
produce errors. Saves use a temporary file and replacement to avoid partial
JSON writes. 
The existing explicit wardrobe argument to `run_agent` still supports isolated
evaluation; automatic persistence is provided by the CLI.
